# OVARA P2.2 — IDENTITY + CREDENTIAL LIFECYCLE

Status: implemented, verified in test environment.
Closes: I1 (identity authenticity), I2 (identity stability across rotation),
I3 (credential revocation). Prepares I20 (revocation propagation).
Scope boundary: no anchoring, no containment redesign, no integrity monitor,
no distributed identity, no consensus. P2.1 replay semantics unchanged.
RC1 remains the immutable regression baseline (46/46 green, unchanged semantics
when the registry is not configured).

---

## 1. STABLE IDENTITY MODEL

An `Identity` is a durable record independent of any single credential:

    Identity{
      ID          string   // "ag_<sha256(first_credential)[:16]>" or "op_..."
      Role        string   // "agent" | "operator"
      Status      string   // active | suspended | retired | migrated
      Generation  uint64   // monotonically increasing per identity
      CreatedAt   time.Time
      RetiredAt   *time.Time
      MigratedTo  string   // set when status=migrated
      Metadata    map[string]string   // operator-supplied, non-authorizing
    }

The identity ID namespace IS the existing RC1 principal namespace: for a
seeded credential `T`, its bound identity is `ag_` or `op_` +
`sha256(T)[:16]` — exactly the string RC1 computed as `principal_id`.
Consequences:

- No stored artifact (lease, delegation, approval, decision, continuation,
  receipt) changes meaning under P2.2. Authorization objects remain bound
  to the same identity strings they were bound to under RC1.
- The migration requirement ("existing credentials must not silently change
  security meaning") is satisfied structurally: a credential's identity
  cannot change without changing the principal string every existing
  artifact references.

Identity IDs are generated by Ovara (`register` without `identity_id`) or
externally supplied. Supplied IDs are allowed because the ID is not a
secret: squatting a string grants nothing — the binding is enforced by the
credential record, and only the holder of a credential bound to that ID can
authenticate as it. Re-registering an existing or tombstoned ID is rejected
with `ErrIdentityExists`.

Retirement is a tombstone, not deletion: a retired identity's record remains
in the registry so the ID can never be silently re-registered or re-
authenticated (prevents resurrection and squatting after death). A suspended
identity retains all state; resume restores authentication.

## 2. CREDENTIAL MODEL

    Credential{
      ID           string    // "cred_<rand>"
      IdentityID   string    // binding target — server-side, immutable
      Fingerprint  string    // sha256(presented bearer token)
      State        string    // active | rotating | superseded | revoked | expired
      IssuedAt     time.Time
      ExpiresAt    *time.Time   // nil = no expiry
      RotatingUntil *time.Time // grace window end, set on rotation
      SupersededAt *time.Time
      RevokedAt    *time.Time
      RotationGen  uint64
    }

The raw bearer token is NEVER stored. Only its SHA-256 fingerprint is
persisted; lookup hashes the presented token and compares fingerprints.
Operator tokens configured in `operator_tokens` are seeded at startup with
identity `op_<fp16>`; agent tokens in `agent_tokens` get `ag_<fp16>` —
identical to RC1 principal derivation.

Generated rotation/registration tokens use a `tok_<rand>` prefix and are
returned exactly once in the API response. No token value is logged or
written to receipts, events, or error output.

## 3. BINDING MODEL

    bearer token
      → sha256(token) = fingerprint
      → registry lookup fingerprint → credential record
      → credential.identity_id = stable identity
      → principal = identity_id

The identity is determined exclusively by the credential record. No request
field can influence it: `bindIdentity` (unchanged from RC1) rejects any
request whose subject/body identity differs from the authenticated
principal before evaluation. The middleware checks the credential; the
identity it returns is authoritative.

Unknown fingerprints fail closed. In registry mode the legacy "no tokens
configured → deny" guard is bypassed because the registry itself is the
authoritative (and fail-closed) source — an empty registry authenticates
nothing.

## 4. LIFECYCLE STATE MACHINES

### Identity

    (created) → ACTIVE
    ACTIVE → SUSPENDED        (operator action; auth fails while suspended)
    SUSPENDED → ACTIVE        (resume)
    ACTIVE → RETIRED          (tombstone; terminal)
    SUSPENDED → RETIRED
    ACTIVE → MIGRATED         (to another identity; terminal for auth)
    MIGRATED → RETIRED

A retired or migrated identity never authenticates and cannot be
re-registered.

### Credential

    ISSUED → ACTIVE
    ACTIVE → ROTATING          (on rotation; authenticates until
                                rotating_until, then → SUPERSEDED)
    ACTIVE → EXPIRED           (at expires_at; lazy transition)
    ROTATING → REVOKED         (revoke always wins — a revoked rotating
                                credential fails immediately, not at grace end)
    ACTIVE → REVOKED
    EXPIRED → REVOKED          (tombstone completeness)

Deterministic ordering in `credStateAt`: REVOKED > SUPERSEDED > EXPIRED >
ROTATING-within-grace > ROTATING-past-grace(=SUPERSEDED) > ACTIVE-within-
expiry > EXPIRED. State transitions are computed from stored timestamps
plus wall-clock at read time (pure function — no lazy mutation), and
records are opportunistically normalized on the next write pass so
persisted state converges.

### Rotation semantics (explicit decision)

Rotation puts all ACTIVE credentials of the identity into ROTATING with a
caller-specified grace window (default 60s, max 24h) and issues the new
credential ACTIVE bound to the SAME identity. Dual validity exists only
inside the grace window: the old credential authenticates to the same
identity (never a different one) until `rotating_until`. After grace it is
SUPERSEDED and fails. A revoked credential fails immediately regardless of
grace — revocation beats the rotating state. `grace_seconds=0` gives
hard-cut rotation (old credential dies at once).

The `RotatingUntil` field is deliberately retained on superseded records so
the history of the dual-validity window is auditable.

## 5. FAILURE SEMANTICS

- Registry configured (`identity_file`) but unreadable/corrupt at startup:
  gateway refuses to start. No silent in-memory fallback.
- `Authenticate` on a store whose persistence failed: the record may exist
  in memory (writes are clone→mutate→persist→commit, so a failed persist
  leaves memory unchanged) but the next write fails; authentication of
  records already committed is unaffected. A store that cannot load is
  never constructed — fail closed at startup.
- Unknown fingerprint, malformed bearer, expired/revoked/superseded
  credential, suspended/retired/migrated identity → 401, with a
  `WWW-Authenticate` challenge. Timing is not secret-dependent beyond the
  hash+map lookup.
- Persistence corruption mid-file: `load` requires every JSON line to
  parse and every record to validate (non-empty IDs, known states, valid
  references). Any violation → open error → startup refusal.

## 6. PERSISTENCE MODEL

Single JSON-lines file (same format family as the P2.1 replay journal:
one record per line, whole-object snapshots — identities and credentials
share one journal). Writes use `persist.WriteFileAtomic` (temp + fsync +
rename + dir fsync) under an exclusive `flock`, so cross-process
registration/rotation/revocation serialize correctly. In-memory indexes
(identity ID → record, fingerprint → credential) are rebuilt on load.

When `identity_file` is unset, an in-memory registry seeds from
`agent_tokens`/`operator_tokens` at startup — preserving RC1 semantics
byte-for-byte (verified: RC1 harness 46/46) — so P2.2 is opt-in by
explicit configuration, symmetric with P2.1's `replay_file`.

## 6a. AUTHORITY MODEL — WHAT REVOKING EACH OBJECT INVALIDATES

Two distinct revocation layers, deliberately separated:

- **Credential-level**: kills one bearer token's ability to authenticate.
  Identity-bound objects are unaffected — they were granted to the
  identity, and any other live credential of that identity may use them.
- **Identity-level**: kills the identity. Authentication fails for EVERY
  credential; identity-bound objects cannot be exercised because no
  authentication path exists to reach them; queued work is never claimed.

| Event                    | Credential | Identity | Delegation | Lease | Approval | Continuation |
|---|---|---|---|---|---|---|
| Credential revoked       | dead       | active   | usable by other live creds | usable | resumable | executes for identity |
| Credential expired       | dead       | active   | (same as revoked) | (same) | (same) | (same) |
| Credential superseded    | dead       | active   | (same) | (same) | (same) | (same) |
| Identity suspended       | all 401    | dead*    | unusable (401) | unusable | queues, never claims | never claims/executes |
| Identity retired         | all 401    | dead     | unusable | unusable | queues, never claims | never claims; tombstone |
| Identity migrated        | all 401    | dead→target | unusable | unusable | never claims | never claims |
| Lease revoked (tracked)  | unchanged  | active   | n/a | dead (denied at eval) | n/a | n/a |
| Approval consumed        | unchanged  | active   | n/a | n/a | single-use spent | n/a |
| Credential rotated       | old→grace  | active   | unchanged — bound to identity | unchanged | unchanged | unchanged |

*suspended = recoverable death; resume restores all of it.

Two documented gaps in this table, both deliberate:

- **Delegation revocation does not exist.** Delegations are stateless
  signed chains; only P2.1 replay bounds re-presentation of the SAME
  presentation_id, and expiry bounds lifetime. A legitimately-minted
  delegation for ID-A remains usable by any live ID-A credential until
  expiry — only identity suspension/retirement stops it. Issuer
  revocation likewise does not exist (trusted_issuers is config).
  **P2.3 dependency** (I20 revocation propagation).
- **Lease revocation covers TRACKED leases only** (`capabilities/track`
  → `revoke`/`revoke-by-subject`). RC1 semantics: an untracked lease
  presented at check time is validated cryptographically, not against
  the tracking store. Unchanged by P2.2.

## 6b. STOLEN CREDENTIAL CONTAINMENT — THE EXPLICIT CONSEQUENCE

Scenario: attacker uses stolen C1 to create delegation-usages, approvals,
and queued continuations bound to ID-A. Operator revokes C1.

Result (verified e2e): C1 is dead — it cannot authenticate, evaluate,
approve, or execute. **But the objects it created remain valid for ID-A**
because they were never bound to C1 — they were bound to the identity.
A legitimate C2 of ID-A can exercise them.

**Credential revocation does not retroactively revoke authorization
objects owned by the identity.** This is the intentional model (a
credential is a means of authentication, not the unit of ownership),
and the containment consequence is explicit: responding to a
*compromised* credential requires EITHER

- identity suspension (kill-all: auth + objects + queued work), or
- per-object revocation where it exists (tracked leases via
  `revoke-by-subject`), or
- approval denial of the pending escalation.

Operators who suspect credential theft should suspend the identity and
audit its pending approvals/continuations before resuming — revocation
alone only stops the attacker's credential, not the attacker's prior
authorized grants to the identity.

## 6c. CONTINUATION ENFORCEMENT POINTS

Identity gating exists at BOTH execution entry points:

- `Orchestrator.drainQueue` — skips candidates whose `AgentID` resolves
  to a non-active identity (queued, never claimed; claimable on resume).
- `POST /v1/continuations/{id}/execute` — the synchronous operator path
  re-checks after claim and requeues + 409 on non-active identity.
  This gate was added during the conditional review: previously the
  direct endpoint bypassed the suspension semantic (found by attacking
  the continuation path, fixed minimally, regression-tested e2e).

Approval `/resume` only re-queues — the claim gate covers it. `enqueue`,
`retry`, `recover-executing` all re-queue → claim gate covers them.
In-flight executions at suspend time are NOT killed (bounded by their
timeout); suspension prevents new claims, it does not abort running work.
Continuation store is in-memory by default (RC1): restart drops queued
work — identity state, which IS durable, still prevents re-execution of
anything re-submitted by a dead identity.

## 7. DELEGATION INTERACTION

Delegation subject binding is unchanged: the chain's subject must equal
the authenticated principal (`bindIdentity` + evaluator subject check —
both untouched). Under P2.2 the principal IS the stable identity, so:

- C1 → ID-A, delegation subject = ID-A → ALLOW (verified e2e)
- C1 → ID-A, delegation subject = ID-B → DENY (verified e2e)
- After rotation, C2 → ID-A with the same delegation → ALLOW (verified
  e2e): the delegation outlives the credential because it is bound to the
  identity, which is the documented design goal (I2).
- Revoked C1 → authentication fails before delegation evaluation; the
  delegation cannot be consumed by that credential. Another valid
  credential bound to ID-A can still use it — delegation validity follows
  the identity, not the credential. This is the explicit design decision:
  a delegation grants the identity, so identity suspension (not credential
  revocation) is the control that kills an identity's delegated power.
  Suspension was verified to block authentication entirely.

## 8. LEASE / APPROVAL / CONTINUATION INTERACTION

Same rule throughout: leases, approvals, decisions, continuations, and
receipts are keyed by identity string and were already bound to the RC1
principal — which is now by construction the stable identity. Rotation
therefore cannot orphan or transfer them. Revoked or superseded
credentials fail at the auth boundary; a different live credential of the
same identity exercises the same leases/approvals — correct, because they
were granted to the identity.

Suspended identities additionally cannot execute queued work: the
orchestrator's claim filter skips candidates whose
`Continuation.AgentID` resolves to a non-active identity
(`SetIdentityChecker`). A queued continuation becomes executable again if
the identity is resumed. This closes the revoke-then-run-stale-work gap:
the only way stale work survives is if the IDENTITY is still active — in
which case it is legitimately live.

## 9. PROXY INTERACTION

The proxy no longer derives its identity locally by hashing its token.
`client.whoamiIdentity` lazily calls `GET /v1/whoami` (agent-accessible)
with the bearer token and caches the returned principal; if the endpoint
is unavailable (e.g. mixed-version deployment) it falls back to the RC1
hash derivation, which the gateway's `bindIdentity` still enforces — so
the fallback cannot widen the accepted identity. Result: the proxy
presents the gateway-authenticated identity verbatim; a rotated proxy
credential automatically resolves to the same stable identity without
reconfiguration, and a revoked proxy credential fails at the gateway.

## 10. MIGRATION FROM RC1

| surface | RC1 | P2.2 |
|---|---|---|
| principal | sha256-derived string | identical string, now a registry identity |
| token storage | plaintext config | fingerprints; config tokens seeded as creds |
| rotation | none (restart + reconfigure) | API rotation, identity preserved |
| revocation | none | per-credential, durable, survives restart |
| artifacts | bound to principal | unchanged — same strings |
| registry absent | — | in-memory, seeds config tokens = RC1 mode |

Migration is therefore: set `identity_file`, keep existing `agent_tokens` /
`operator_tokens`. Seeded credentials reproduce the RC1 principal exactly —
nothing needs re-issuance and nothing changes hands. If `identity_file`
points to a path with existing P2.2 state, seeded config tokens MERGE (a
config token that is also a live registry cred keeps its state — including
`revoked`, so an operator cannot accidentally un-revoke by restarting with
the token still in config; a genuinely new config token is added as a new
credential on its derived identity, even if that identity already exists —
this is deliberate recovery semantics: config remains a bootstrap path).

## 11. GATEWAY IDENTITY / ENROLLMENT (D-08 disposition)

D-08 (gateway identity keys) is NOT implemented in P2.2 and is hereby
marked a **P2.3 REQUIRED DESIGN ITEM**.

CURRENT: gateway identity is a filesystem-backed, cloneable identity —
an enrollment file plus operator tokens. Identity registration and
lifecycle operations are protected by operator tokens, not by a
hardware/PKI-bound gateway identity. A second Ovara instance sharing the
`identity_file` participates in the same trust domain by filesystem
possession — the same "single trusted state domain" boundary as P2.1's
journal.

THREAT: T-ENROLL-CLONE — the gateway identity is not cryptographically
bound to a unique gateway instance; audience binding (delegation/lease
`audience` fields) therefore authenticates the trust domain, not the
specific gateway.

CONSEQUENCE: P2.2 makes NO claim that gateway identity is
cryptographically authenticated. The accurate claim is: **gateway
identity is currently a filesystem/trust-domain membership property.**
Mitigation requires the D-08 key mechanism — deferred to P2.3.

## 12. THREAT MODEL

| threat | handling |
|---|---|
| stolen active credential | authenticates — this is the credential model; mitigation is revocation (tested: immediate + durable) |
| revoked credential reuse | 401 at auth boundary; survives restart (tested) |
| credential→wrong-identity claim | binding is server-side; request cannot choose identity (tested: subject substitution 400) |
| cross-identity delegation | subject mismatch → deny (tested) |
| agent→operator escalation | role separation preserved: agent token gets 403 on all `/v1/identities/*` admin routes (tested); seeded roles come from which config list the token is in |
| identity resurrection | retired/migrated tombstones block re-registration (tested: 400 conflict) |
| identity squatting | supplied IDs allowed but confer nothing; existing IDs rejected |
| rotation race | single flock-serialized mutation; concurrent rotates serialize — last wins, all prior creds rotating (unit-tested) |
| revocation vs auth race | no TOCTOU stronger than storage: auth checks state at request time; a revoke committed mid-request affects the NEXT request. Not claimed as stronger. |
| registry rollback/deletion | same class as P2.1 journal rollback: restoring an old file resurrects revoked creds — needs anchoring, deferred |
| secret leakage | fingerprints only in store; token returned once at issuance; no logging (swept) |

## 13. SECURITY INVARIANTS

- Revocation is IMMEDIATE for the credential — the next authentication
  attempt fails. It is NOT claimed to be immediate for identity-bound
  authorization objects: those follow the identity (see §6a). The
  mechanism that kills an identity's delegated authority is identity
  suspension/retirement, not credential revocation.
- A credential authenticates only the identity it is bound to; the binding
  is set at issuance/rotation and immutable thereafter.
- The caller can never select the identity; request-supplied identity
  fields that disagree with the authenticated principal are rejected
  before evaluation (RC1 `bindIdentity`, unchanged).
- Revocation beats every other state; a revoked credential never
  authenticates, under any grace window.
- Identity state and credential state are different machines: credential
  death ≠ identity death. Delegations/leases/approvals follow the
  identity.
- Registry mode never falls back to in-memory or allow-all on failure.

## 15. KNOWN LIMITATIONS

- Rollback of `identity_file` resurrects revoked credentials —
  undetectable locally; requires receipt/state anchoring (deferred, same
  class as P2.1 journal rollback).
- Trust domain is one filesystem's `flock` — cross-host identity
  consistency is architectural (I20 propagation is a later milestone).
- Auth-vs-revoke is a commit-ordering race, not a transactional cutoff.
- Credential revocation is NOT object revocation (§6b): a compromised
  credential's prior grants to the identity remain until the identity is
  suspended or the objects are revoked/expired — documented consequence,
  containment = suspend + audit.
- Delegation + issuer revocation do not exist (stateless signed chains;
  trusted_issuers is config) — P2.3 dependency (I20).
- Lease revocation covers tracked leases only (RC1 semantics, unchanged).
- Gateway identity is filesystem/trust-domain membership, not crypto-
  graphic instance authentication — D-08 marked P2.3 REQUIRED.
- In-flight executions are not aborted by suspension (bounded by
  executor timeout); suspension blocks new claims only.
- Continuation store is in-memory by default: restart drops queued work.
- `grace_seconds` max 24h — operator-set; longer dual-validity is a
  policy choice, not a code limit.
- Seeded credentials have no expiry by default (RC1 parity); set
  `expires_seconds` at registration for API-registered creds.
- In-memory mode (no `identity_file`) provides lifecycle APIs but no
  persistence — documented as RC1-equivalent, not a silent durability
  promise.
